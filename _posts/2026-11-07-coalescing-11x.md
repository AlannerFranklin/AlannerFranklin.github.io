title: 同一个加法，为什么慢了 11.3 倍
---

两个几乎一模一样的加法 kernel，只改了一行索引计算：一个跑 0.0069ms，一个跑 0.0778ms，慢了 11.3 倍。

## 实验

两个 kernel 做同一件事：`c[i] = a[i] + b[i]`，N = 1e6，共 12MB 数据。唯一的区别是索引公式：

```c
// 合并版：blockIdx.x * blockDim.x + threadIdx.x
// 散开版：threadIdx.x * gridDim.x + blockIdx.x
```

合并版里相邻线程访问相邻元素；散开版里相邻线程的地址相隔 `gridDim`（3907）个元素，隔得太远。

实测（4070 Ti Super + nvcc 12.6，预热 1 轮 + 3 轮取最小）：

| kernel | 耗时 | 带宽 |
|---|---|---|
| 合并版 | 0.0069 ms | 1744 GB/s |
| 散开版 | 0.0778 ms | 154 GB/s |

**ratio = 11.31。**

## 为什么

GPU 读显存不是按字节，而是按 **32 字节的 sector** 交易——一次交易固定 32 字节。

一个 warp 有 32 个线程。合并版里 32 个线程读的是连续的 128 字节，恰好 **4 笔**交易，字节全部有用。散开版里 32 个线程落在 **32 个**不同的 sector 里，每笔 32 字节只用了 4 字节，利用率只有 12.5%。交易量变成 8 倍——12MB 有用数据，背后实际交易了 12 × 8 = **96MB**。

还有第二层损耗。L2 处理每笔交易都要占一个请求槽位：合并版一个 warp 只下 4 笔单，散开版要下 32 笔。单子一多，单位时间能服务的字节数就下降——合并版的 sector 吞吐是 1744 GB/s，散开版只有 1234 GB/s，又慢了 1.4 倍。

所以：

```
11.31 ≈ 8（流量浪费）× 1.4（请求排队损耗）
```

还有一个反直觉的细节：1744 GB/s 超过了这张卡 672 GB/s 的显存峰值——因为 12MB 数据整个塞进了 48MB 的 L2 缓存，测到的是 L2 带宽。真实场景的数组都大于 L2，散开访问会直接落到显存随机寻址上，差距会比 11.31 更狠。

## 一个坑

这个实验是我配好 CUDA 环境后的第一次编译。CUDA 12.6 配的是家里现成的 VS 2026，结果 nvcc 直接报错：

```
#error: unsupported Microsoft Visual Studio version!
Only the versions between 2017 and 2022 (inclusive) are supported!
```

nvcc 12.6 官方支持的 MSVC 上限是 VS 2022 系列，VS 2026 的 MSVC 对它来说太新。解决：补装了 VS 2022 Build Tools（MSVC 19.44）到 E:\BuildTools，编译通过。

教训：CUDA 工具链和宿主编译器的版本要**一起**看，只查 CUDA 版本是不够的。

## 结论

GPU 编程不是写逻辑，是写访存。让相邻线程访问相邻地址，按 sector 的搬运方式把每笔交易用满——这一行索引公式，就值 11.3 倍。
