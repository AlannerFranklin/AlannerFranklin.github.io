title: 矩阵乘法三连：从 2.3 到 13.7 TFLOPS
---

同一个 1024×1024 的矩阵乘法，三个版本：naive → tiled → reg。实测（RTX 4070 Ti Super + nvcc 12.6，N=4096）耗时从 58.79ms 一路降到 10.06ms，**5.8 倍**；算力从 2.3 TFLOPS 涨到 13.7 TFLOPS，达到这张卡 FP32 峰值（44.1T）的 31%。

| 版本 | 每线程输出 | 改了什么 | N=4096 耗时 | GFLOPS |
|---|---|---|---|---|
| naive | 1 | 直接读全局内存 | 58.79 ms | 2,338 |
| tiled | 1 | 先搬进 `__shared__` 再算 | 45.56 ms | 3,016 |
| reg | 4×4=16 | 累加器放寄存器 | 10.06 ms | 13,660 |

## 版本一 naive：2 次 load 养 1 次乘加

每个线程算一个输出：`sum += A[row*N+k] * B[k*N+col]`，k 循环 N 次。

它的死穴在**指令结构**：每做 1 次乘加，要先做 2 次 load；而且 `sum` 是串行依赖链——这一次的乘加必须等上一次的 sum 出来。全 GPU 加起来要读 2N³ 次。

## 版本二 tiled：换了读的地方，没减读的次数

用 `__shared__` 把 A、B 的 32×32 子块先搬进 SM 片上内存，块内 1024 个线程共享——global 读量降到 2N³/32。两个 `__syncthreads()`：填完 shared 后的那个防 RAW，本轮读完、下一轮写之前的那个防 WAR。删掉任何一个都不会崩，只是数不对。

**但它只快了 1.2 倍。** 读数账说明一切：

```
naive: 读 global 2N³ 次 —— 但 A+B 只有 8MB，全在 48MB 的 L2 里
tiled: 读 global 2N³/32 次 + 读 shared 2N³×31/32 次 —— 总次数还是 2N³
```

tiled **没有减少读的次数，只是换了读的地方**。而 naive 的重复读本来就命中 L2、没走到 DRAM——tiled 的"药效"被 L2 提前兑现了。这也是为什么白天 AI 预测 2-4 倍，实测只有 1.29 倍。

## 版本三 reg：减读的次数，才是真起飞

设计：`block(32,8)` = 256 线程，每线程算 4×4=16 个输出，累加器 `acc[4][4]` 放**寄存器**；tile 扩成 32 行×128 列（`Bs[32][128]`）。

内层每个 k：**8 次 shared load 养 16 次乘加**（tiled 是 2 养 1）。整个 kernel 的 load 次数从 2N³ 降到 N³/2，乘加/读的比例从 0.5 升到 2.0。

这里有个我卡了一整天的坑：**三层坐标映射**。blockIdx 一层、ty/tx 一层、线程内 i/j 一层，三层叠在一起直接超出我的工作记忆：

```
C 的行 = blockIdx.y × 32 + threadIdx.y × 4 + i     (i = 0..3)
C 的列 = blockIdx.x × 128 + threadIdx.x + j × 32   (j = 0..3)
```

第二天用 N=256 的小例子，把 C 画成表格、圈出一个线程负责的 16 个格子，才真正通了。事后总结出一条规则：**块内号 = 连续的那个 + 另一个 × 连续那个的总数**（行 `i + ty×4`，列 `tx + j×32`）；列故意用交织切分（tx 连续、j 跳 32），是为了让一个 warp 的 32 个线程铺满 32 个 bank。

occupancy 账：约 34 寄存器/线程 × 256 = 8704/block，`65536÷8704=7`，线程上限 `1536÷256=6`，取 min = 6 block/SM → **100% occupancy**。

结果：**4.5 倍于 tiled**（10.06ms vs 45.56ms）。用 ncu 验证时还踩了个坑：普通终端报 `ERR_NVGPUCTRPERM`，要管理员权限才能采计数器。拿到数之后两个判据全过：`local_ld = 0`（累加器确实全进了寄存器）、DRAM 流量 4.35GB。

## Roofline 实测：还在 memory-bound 区

```
FLOP     = 2 × 4096³ = 1.374e11
AI       = 1.374e11 ÷ 4.35e9 = 31.6 FLOP/byte
ridge point = 44.1e12 ÷ 672e9 = 65.6 FLOP/byte
AI < 65.6 → memory-bound
带宽天花板 = 672 × 31.6 = 21,235 GFLOPS
完成度    = 13,660 ÷ 21,235 = 64%
```

下一步是 8×8 版：按公式 AI 会翻倍到 ≈63，**几乎正好踩在 ridge point 上**——一脚踩在 memory-bound 和 compute-bound 的分界线上。代价是 occupancy 掉到 50%，换不换得来，测了才知道。

## 两个教训

1. **预测会落空，实测不会**：白天 AI 预测 tiled 快 2-4 倍（实测 1.29）、4096 拉开 3-10 倍（实测 1.16），两次全落空。之后它拒绝给预测，只给红线："reg 比 tiled 慢 = 一定有 bug"。红线通过了，大胜 4.5 倍。
2. **tiled 换读的地方，reg 才减读的次数**——性能优化的每一级台阶，都要先数清楚"次数"这笔账。
